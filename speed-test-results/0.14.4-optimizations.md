# Quiesco 0.14.4 之后还能优化的地方

依据 2026-11-27 的 0.14.4 测量结果整理。数据来源：

- 正式测量：`speed-test-results/0.14.4.json`（m5-quiesco-0144，iOS / Android 各 N = 20）
- 逐步骤 timeline：rn-e2e-shootout `suites/quiesco/artifacts/20261127-231423-ios/`（Quiesco 0.14.4、iOS、24 个场景各 1 次，`QUIESCO_TIMELINE=all`）
- shootout 的 `findings.md` “为什么 iOS 上 Quiesco 有些场景比 Appium 慢（逐步骤对比）”一节
- 本机实测的 simctl 调用耗时（`Shootout iPhone 17`，41F17B68）

结论先行：Android 上 Quiesco 已经在所有场景最快或打平，下面这些都集中在 **iOS**。按对跑分（`scenarioMs` / 共同场景集整套耗时）的影响从大到小排列。

## 1. `relaunch({ clearData: true })` 的 simctl 调用链

shootout 每个场景的 `beforeEach` 都调用 `app.device.relaunch({ clearData: true })`，它在 iOS 上**串行**执行：

| 步骤 | 调用 | 实测耗时 |
|---|---|---|
| `device.ts` `relaunch()` | `simctl terminate` | ~180 ms |
| `ios.ts` `clearData()` | `simctl terminate`（**第二次，多余**） | ~180 ms |
|  | `simctl spawn … defaults delete` | ~330 ms |
|  | `simctl get_app_container … data`（每次都查） | ~185 ms |
|  | 删除 Documents / Library / tmp | 小 |
| `ios.ts` `launch()` | `simctl launch --terminate-running-process` | 未单独测 |

（`simctl` 每次调用的进程启动开销约 160–180 ms；`spawn` 要在模拟器里再起一个进程，约 330 ms。）

可做的改动：

- `clearData()` 里的 `terminate()` 在 `relaunch()` 路径上是重复的：加个参数跳过，或由调用方保证已经终止。省约 0.18 s。
- 数据容器路径在一个会话内、没有重装时不变：缓存 `get_app_container` 的结果（重装 / uninstall 时清掉）。省约 0.18 s。
- `defaults delete` 和删除目录互不依赖，可以并行。省约 0.1–0.2 s。

合计每个场景约 0.35–0.5 s。iOS 重置的 `resetMs` 中位数约 3.0 s（Android 约 2.0 s），这一项能解释其中一部分差距。

验证：改完后用 `QUIESCO_TIMELINE=all` 跑一轮，看 harness 的 `resetMs`；再按 METHODOLOGY 正式测 N = 20。

**实施（2026-11-28，分支 `perf/ios-reset-path`）**：`relaunch()` 调用 `clearData({ terminated: true })`，跳过第二次 terminate；数据容器路径缓存到下次 install / uninstall，文件夹不存在时重新查询。defaults delete 与删除目录的并行没有做：路径缓存后删除目录只要几毫秒，并行几乎没有收益，反而要考虑和 cfprefsd 的先后顺序。

实测（临时工程用本地 core 驱动 shootout 的 Release 构建，同一台模拟器，每个阶段 8 个类似 S2 的场景，中位数）：`clearData` 302–314 ms。改动前按同一次测得的各调用耗时（`terminate` 162 ms、`get_app_container` 约 185 ms）推算约 0.66 s，每个场景省约 0.35 s。

## 2. runner 运行时 app 启动变慢

- 0.13.4：runner 在 S8 第一次用 `system.*` 时才启动。S1–S8 的 `resetMs` 约 2.6 s，S9 之后约 3.0–3.5 s。
- 0.14.4：runner 在会话开始后就在后台启动（`warmUpSystemUi`），所有场景的 `resetMs` 都约 3.0 s。S1 / S2 多了 0.9 s / 0.8 s，因为这时 runner 还在启动、抢资源。
- 0.14.3 的 perf 提交（`6173358`）的说明里也写了：“A running runner makes each app launch ~0.45 s slower”。

24 个场景 × 约 0.4 s，相当于每轮约 10 s，是目前最大的一块。原因还没查清，可能是 XCUITest 的 automation / 辅助功能会话让 app 启动变慢，需要测了才能确定。

查法：在同一台模拟器上，分别在 runner 运行和未运行时，测 `simctl launch` 到 agent 连上（`agent connected`）的时间，各 10 次以上。如果确实是 runner 造成的，再看能否只在需要时让 runner 保持 automation 会话，或者在 relaunch 期间暂停它。

**实测结果（2026-11-28，同上的临时工程，runner 未运行 / 运行中各 8 个场景，中位数）**：

| 步骤 | runner 未运行 | runner 运行中 | 差 |
|---|---|---|---|
| `simctl launch` | 186 ms | 189 ms | 0 |
| launch → agent 连上 | 1617 ms | 2064 ms | +447 ms |
| 重置（`resetMs`，含上一行） | 2293 ms | 2713 ms | +420 ms |
| 重置结束 → 第一个 `type` 完成 | 2619 ms | 2321 ms | −298 ms |
| 场景合计（`scenarioMs`） | 5867 ms | 6001 ms | **+134 ms** |

runner 运行时 app 连上确实晚约 0.45 s，但连上之后的启动收尾也相应变短，第一个操作快了约 0.3 s。所以单个场景的净影响只有约 0.13 s，24 个场景约 3 s，比原来估计的 10 s 小得多。基准中 0.13.4 → 0.14.4 的 `resetMs` 增加（约 +0.4 s）也大多是这种挪动。考虑到预热换来了 S8 −7 s、S21 −4 s，暂不处理。

## 3. 断言前的空闲等待

timeline 中每个断言开始时都要先等约 75 ms：frame-stable 报 “no frame rendered yet”，要等两次检查都空闲才算确认。即使上一步刚确认过空闲、中间什么都没做，也一样要等。

- 一轮 iOS 共 46 个断言，`assert` 的等待合计 6.4 s，其中这种固定开销约 3.5 s。
- 改法设想：如果上一次空闲确认之后没有发出任何操作，而且各 tracker 都没有新的活动，就跳过 frame-stable 的新帧要求，或者缩短确认间隔。

风险：在“上一步之后 app 自己又开始动”的情况下（定时器触发、轮询），跳过等待可能断言到中间状态。需要先确认 tracker 能否可靠地报告“自上次确认后有无活动”。

## 4. 操作前的空闲等待（与 Appium 的差距）

shootout 的逐步骤对比（S1 等）显示：Quiesco 每个操作前都等 app 完全空闲，`tap` 前的等待中位数约 0.63 s。Appium 只等 UIKit 静止，目标元素一出现就继续。所以在简单的顺序操作里，Quiesco 每步多等约 0.3 s。iOS 上 Quiesco 比 Appium 慢的场景（S1、S10a、S11、S15、S16、S18、S20，差 0.1–0.7 s）基本都是这个原因。

这一轮 timeline 中等待最后结束于哪个 tracker（合计秒数）：native 75 s、react 29 s、timer 16 s、frame-stable 8 s、network 1 s。

可以考虑的点：

- **键盘静止窗口** `KeyboardMotion.quietSeconds = 0.4`（`packages/native/ios/QuiescoNativeModule.swift`）。注释里写着实测“输入后 0 ms 点击会被丢掉，300 ms 后能送达”。缩短到 0.3 s 每次省 0.1 s，但余量变小。
- **30–80 ms 的短 JS 定时器也算忙碌**（timer tracker 的阈值是 1500 ms）。这些多是防抖或状态切换，等它们是正确的行为，不建议改。

结论：这部分是灰盒“等到真正就绪”的代价，也是稳定性的来源。收益小、风险大，不建议先做。

## 5. soft reset 与用户的 relaunch 重复（不影响跑分）

`session.ts` `beforeScenario()` → `resetForScenario()` 在每个场景前会做：撤销设备状态（`resetDeviceState`）、soft reset（`driver.reset()`），iOS 上还会检查残留的系统弹窗（runner 运行时调用 `runner.screen()`）。timeline 中 iOS 这一步每个场景约 1.07 s。

shootout 的 `beforeEach` 接着又执行 `relaunch({ clearData: true })`，所以前面的 soft reset 完全白做。另外，上个场景调用的 `setPermission('location', 'reset')` 会被记进 `permissionChanges`，下个场景的 `resetDeviceState` 还会多执行一次 `simctl privacy revoke`（约 0.2 s）。

- harness 的计时标记在 soft reset 之后，所以这一步**不计入**跑分。
- 但对用户来说是实际耗时：每轮 iOS 约 25 s，占总耗时的 8% 左右。用 `beforeEach` 做硬重置的项目都会遇到。

改法设想：把 soft reset 推迟到场景的第一个 app 操作之前执行。如果在那之前已经 relaunch 过（进程是新的、数据已清），就跳过。另外 `setPermission(…, 'reset')` 已经回到初始状态，不必再记进 `permissionChanges`。

**耗时拆分（2026-11-28，同上的临时工程，中位数）**：

| 步骤 | runner 未运行 | runner 运行中 |
|---|---|---|
| 恢复设备状态（`resetDeviceState`）：上个场景的 `setPermission('location', 'reset')` 恢复成撤销（`simctl privacy revoke`） | 179 ms | 236 ms |
| 其中：检查残留系统弹窗（`runner.screen()`） | 0 | 46 ms |
| soft reset（`driver.reset()`），几乎全在 app 侧：清存储、重新挂载，再等空闲 | 468 ms | 461 ms |
| 合计 | 约 0.65 s | 约 0.7 s |

（timeline 里的 1.07 s 还包含 timeline 本身和场景开始的处理，这里只看 reset 的各步。）

- 首页写的“约 200 ms 的重置”和 iOS 实测的约 0.46 s 对不上：重新挂载后等空闲占了大部分。需要另外看一下 Android 上是多少，再决定是改首页文字还是优化等待。
- `privacy revoke` 这一步是文档规定的行为（“权限回到 config 中配置的状态”，没配置的就撤销），不能为了省 0.2 s 去掉。

延迟执行的设计要点（待定）：`beforeScenario` 只做恢复设备状态，soft reset 记为“待执行”；第一次 app 内调用之前执行它；如果在那之前已经 `relaunch({ clearData | reinstall })`，就取消。需要一起考虑的有：`reset.expectVisible`、连接丢失时重启 app 的处理（目前在 `beforeScenario` 里）、timeline 中 reset 的位置，以及 `onReset` 钩子的执行时机。
