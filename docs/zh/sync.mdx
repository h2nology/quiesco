---
title: "同步"
description: "为什么测试不需要 sleep：什么叫空闲，什么会让 App 忙碌，以及 App 一直不空闲时该怎么办。"
---

Quiesco 在每次调用之前和之后，都会等 App **空闲**。测试从不需要 `sleep` 或
`waitFor`：

```ts
// 等待请求、页面跳转和下一屏的渲染
await app.tap('save-todo');

// 在稳定下来的页面上执行
await app.expectVisible('todo-list-screen');
```

## 工作原理 {#how-it-works}

<Steps>
  <Step title="先等待，再操作">
    调用之前，Quiesco 等 App 空闲，然后点击、输入或读取页面。
  </Step>
  <Step title="App 做出反应">
    这次调用会在 App 里引发各种工作：请求、计时器、渲染、动画。
  </Step>
  <Step title="再次等待">
    Quiesco 等所有[跟踪器](#trackers)都空闲，并且相隔一个宏任务连续确认两次，这样在同一个 tick 里启动请求的计时器也不会漏掉。然后调用才返回。
  </Step>
</Steps>

如果过了 `sync.timeoutMs`（10 秒）还在等待，调用会以 `SYNC_TIMEOUT` 失败（见[下文](#when-the-app-never-becomes-idle)）。

## 跟踪器 {#trackers}

App 里的 agent 用下面这些跟踪器判断“空闲”。没有任何一个跟踪器忙碌时，App 就是空闲的。

| 跟踪器 | 忙碌的条件 |
|---|---|
| `network` | 有 `fetch` 或 `XMLHttpRequest` 正在进行，或者 `WebSocket` / `EventSource` 正在连接 |
| `timer` | 有不超过 1.5 秒的 `setTimeout` 等待执行 |
| `react` | React 还有渲染或 effect 没执行完 |
| `idle-callback` | 有 `requestIdleCallback` 等待执行 |
| `native`（仅 iOS） | 页面切换或键盘正在动画中 |
| `frame-stable` | 最近 2 帧内画面有变化：UI 线程上的动画 |
| `native-module`（需开启） | 有原生模块调用尚未结束，最多算 2 秒（[详情](#native-module-calls)） |

关闭某个跟踪器：

```ts
sync: { trackers: { 'frame-stable': false } }
```

<AccordionGroup>
  <Accordion title="network">
    - `fetch` 在响应到达之前都算忙碌。紧接着读取响应体（`json()`、`text()`……）时，会一直忙到响应体读完。
    - `expo/fetch` 同样会被跟踪。基于 XHR 实现的 `fetch`（React Native）只算一次。
    - `WebSocket` / `EventSource` 只在打开、失败或关闭之前算忙碌。已打开的连接从不算，agent 自己的连接也不算。
    - `sync.ignoreUrls` 可以排除长轮询、SSE 和统计请求。
  </Accordion>
  <Accordion title="timer">
    - 只有不超过 `sync.timerThresholdMs`（1.5 秒）的计时器才算：30 秒的会话超时不会阻塞。
    - `setInterval` 只有在 `sync.countIntervals: true` 时才算。
  </Accordion>
  <Accordion title="react">
    - 这个跟踪器通过 React DevTools hook 读取 React 自己的记录：待处理的 lane、已安排的回调，以及 React 调度器里的任务。App 本身不需要任何改动。
    - agent 必须在 React Native 的渲染器加载之前装好这个 hook。`metro.config.js` 里的 `withQuiesco()` 会处理好这一点。
  </Accordion>
  <Accordion title="native (iOS)">
    - 由 `@quiesco/native` 报告：JavaScript 看不到的 UIKit 工作，例如导航和模态页面的切换。
    - 键盘从 UIKit 的 `keyboardWill…` 通知开始，到对应的 `keyboardDid…` 为止算忙碌，最长为动画时长加 0.5 秒。iOS 有时会晚几秒才发出 `keyboardDidShow`，这时设备日志里会有 `[Quiesco] keyboard: no Did notification …`。
  </Accordion>
  <Accordion title="frame-stable">
    - 逐帧比较元素树（类型、testID、文本、取整后的位置和尺寸）。最近 `sync.stableFrames`（2）帧内有变化就算忙碌。
    - 用来兜底在 UI 线程上运行的动画（Reanimated、native driver 的 `Animated`），其他跟踪器看不到这些动画。
    - 只在调用等待期间采样。
  </Accordion>
</AccordionGroup>

## 调用为什么慢，或者为什么返回得太早？ {#timeline}

`timeline.html` 里每次调用的条目都会显示它等待空闲的过程：

- **调用很慢**：每个跟踪器的等待最后卡在什么上，例如 `network: GET https://api.example.com/items (240ms)`。
- **调用返回得太早**：最后几次检查，例如 `+272ms busy: native-module | +276ms idle | +277ms idle (confirmed)`，以及这期间开始或结束的原生模块调用。时间是设备时钟，方便和设备日志对照。

以 `SYNC_TIMEOUT` 失败的调用也有这份记录，`scrollTo` 的每一步也有。

## App 一直不空闲时 {#when-the-app-never-becomes-idle}

调用会以 `SYNC_TIMEOUT` 失败，并列出忙碌的跟踪器：

```
App did not become idle within the 10000ms timeout. Busy:
  - network: GET https://api.example.com/todos (10012ms)
  - timer: setTimeout(poll, 1000ms), fires in 420ms
  - frame-stable: element tree changing: stable for 1/2 frames (580 frames sampled in 9960ms)
    last change: first difference at node 12: Text "Loading 41%" … → Text "Loading 42%" …
```

按忙碌的跟踪器查表：

| 忙碌 | 常见原因 | 解决办法 |
|---|---|---|
| `network` | 一直不结束的请求：长轮询、卡住的后端 | 把 URL 加到 `sync.ignoreUrls`，或者修好后端 / mock |
| `timer` | 不断重新设置的短计时器：轮询、反复重新安排自己的 toast | 该步骤用 `{ sync: false }`，或 `this.app.sync.disableTracker('timer')`，或在 e2e 构建里停掉这个循环 |
| `frame-stable` | 无限循环的动画：spinner、骨架屏闪光、装饰性的光晕 | 给该元素加 testID，并列入 `sync.ignoreElements` |
| `react` | 渲染死循环：effect 里没有条件保护的状态更新 | 这是真正的 bug：修掉它 |

<AccordionGroup>
  <Accordion title="读懂报告">
    - 在超时前不久（一秒以内）还忙碌、但超时那一刻空闲的跟踪器也会列出：`frame-stable (idle at the timeout, busy 12ms before it): …`。“计时器 → 渲染 → 几帧安静”这样的循环有一部分时间是空闲的，超时可能正好落在那里。
    - `frame-stable` 会指出第一个发生变化的元素，`recent changes` 列出最近的几次变化。某个元素反复来回变化时，报告会点出它。
    - 如果等待了很久但 `frames sampled` 很少，说明 UI 线程被饿住了（模拟器负载过高），而不是在播放动画。
    - 超时后 `idle-state.json` 里的 `frame-stable` 显示为空闲，因为它只在调用等待期间采样。它的 `lastWait` 保留了等待结束时报告的内容。
  </Accordion>
  <Accordion title="一直稳定不下来的列表">
    没有 `getItemLayout`、而且行高略有不同的 `FlatList` / `VirtualizedList`，在滚动后可能会不停地添加和移除渲染窗口边缘的那一项：报告里会看到某个元素每次都被添加又移除。调大 `timeoutMs` 没有用；`getItemLayout` 或固定行高通常能解决。
  </Accordion>
  <Accordion title="其他解决办法">
    - **timer**：把 `sync.timerThresholdMs` 调到低于循环的间隔也行，但这会影响整个 App 里所有这么短的计时器。
    - **frame-stable**：如果在动的元素不是装饰，就给该步骤加 `{ sync: false }`，之后再断言需要的内容，或者在 e2e 构建里关掉这个动画。
    - **network**：在 mock 服务器里加一个 `MOCK_STALL` 这样的开关，就能故意重现卡住的后端。
  </Accordion>
</AccordionGroup>

<Note>
  `AGENT_TIMEOUT` 是另一回事：agent 完全没有响应，通常是因为长时间的同步任务堵住了 JS 线程。
</Note>

## 对单次调用跳过同步 {#skipping-sync-for-one-call}

```ts
// 之前和之后都不等待
await this.app.tap('start-spinner', { sync: false });

// 在它转动时断言
await this.app.expectVisible('spinner', { sync: false });
```

## 原生模块调用 {#native-module-calls}

默认情况下，尚未完成的原生模块调用（AsyncStorage、选择器……）不会让 App 处于忙碌状态。所以操作可能返回得太早：

```ts
// fetch：会被跟踪
await api.login(email, password);

// 原生模块的 Promise：默认不跟踪
await AsyncStorage.setItem(TOKEN_KEY, token);

// 下一屏挂载，在 effect 里发请求
router.replace('/');
```

`tap('login-submit')` 可能在 `setItem` 完成之前、下一屏开始之前就返回。两种解决办法：

- 等待下一步需要的东西：`await app.expectVisible('item-row-1')`。
- 或者跟踪原生模块调用：在 e2e 构建里包装它们，然后重启 Metro。

```js
module.exports = withQuiesco(getDefaultConfig(__dirname), { nativeModules: true });
```

启动 Metro 时设置 `EXPO_PUBLIC_QUIESCO_NATIVE_MODULES=1` 效果相同。这样 `native-module` 跟踪器就会开启。它的设置项：

```ts
sync: {
  // 未完成的调用最多算这么久
  nativeCallThresholdMs: 2000,

  // "Module.method"；字符串按子串匹配
  ignoreNativeCalls: ['ExpoLocation.watch'],

  // 在包装了原生模块的构建里关闭它
  // trackers: { 'native-module': false },
}
```

<AccordionGroup>
  <Accordion title="永远不算的调用">
    有些调用在等用户操作，测试回应之前会一直处于未完成状态。它们从不算忙碌：

    - 权限请求：Expo 模块和 `PermissionsAndroid`（`*.request…Permission(s)(Async)`）
    - 日期 / 时间选择器：`RNCDatePicker.open`、`RNCTimePicker.open`
    - `ExpoLocalAuthentication.authenticateAsync`
    - 分享面板：`ShareModule.share`、`ExpoSharing.shareAsync`
    - `ExpoWebBrowser.openBrowserAsync` / `openAuthSessionAsync`
    - 图片和文档选择器
    - 弹窗和操作表：`AlertManager.alertWithArgs`、`DialogManagerAndroid.showAlert`、`ActionSheetManager.show…ActionSheetWithOptions`
    - native driver 动画（`NativeAnimatedModule`）

    `ignoreNativeCalls` 会追加到这个列表；`defaultIgnoreNativeCalls: false` 会让这些调用也计入。其他调用超过 `nativeCallThresholdMs` 后就不再算。timeline 会写出调用名（`native-module: Module.method() 1990ms`），可以把它加到 `ignoreNativeCalls`。

    事件订阅（`addListener(eventName, listener)`、`add…Listener` / `remove…Listener(s)`）只有返回 Promise 时才算，与 `defaultIgnoreNativeCalls` 无关。
  </Accordion>
  <Accordion title="不会被包装的模块">
    - React Native 启动期间、agent 加载之前取得的模块：React Native 自己的模块。只有之后从 `TurboModuleRegistry` 和 Expo 的 `requireNativeModule` 取得的模块才会被包装。
    - Gesture Handler、Reanimated 和 Worklets：它们在 UI 线程的 worklet 里调用自己的模块，需要原生函数。
  </Accordion>
  <Accordion title="没有包装，或关闭了跟踪器时">
    - 没有 `nativeModules: true` 时，这个跟踪器什么都不算：这时设置 `trackers: { 'native-module': true }` 会输出警告，`quiesco doctor` 也会警告。
    - 包装了但关闭了跟踪器时，调用仍会被记录：在调用未完成时就返回的操作会在 timeline 条目里列出它，失败测试的 `idle-state.json` 也会列出（`nativeCallsNotCounted`）。
  </Accordion>
</AccordionGroup>

## 平台说明 {#platform-notes}

- 三个平台运行相同的跟踪器；`native` 只存在于 iOS。
- Web：整页重新加载后 agent 会重新连接，Quiesco 会等它。使用 Expo Router 的静态输出时，hydration 完成后 App 即就绪。

更多内容见[平台差异](./platforms)。
