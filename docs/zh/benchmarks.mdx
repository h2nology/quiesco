使用 `examples/todo-app/bench/run.mts`（在示例 App 中执行 `pnpm bench:android`）测量；参见 requirements.md §8（性能 / 稳定性）。数据来自从 Metro 加载开发版 JS bundle 的 dev client，因此包含开发模式的开销；release 构建会更快。

测量内容：

- **soft reset (agent)**：agent 报告的 `reset` 耗时（清除存储 → onReset 钩子 → 重新挂载 → 等待空闲）。requirements.md §6.5 中的目标：&lt; 500 ms。
- **soft reset (host round trip)**：同上，在 host 端围绕 WebSocket 调用测量。
- **tap incl. sync**：在登录屏幕上 email 为空时执行 `app.tap('login-button')`（显示提示，无网络请求），在 host 端测量：解析目标 + 之前的同步、触摸，以及之后等待空闲的时间。
- **full example suite**：用 `cucumber-js` 运行全部示例 feature，包括安装 APK 和启动 App。

- native 点击比 js 点击多花约 150 ms。构成：50 ms 的触摸按住时间、"视图已停止移动" 检查（相隔一帧的两次原生查询），以及触摸之后 Pressability 的 `minPressDuration` 定时器（130 ms）——定时器跟踪器会正确地等它结束后才重置按下状态。js 模式直接调用 `onPress`，没有这些开销。

## Phase 6.12：并行运行 {#phase-612-parallel-runs}

整套示例测试（86 个场景；iOS 上运行 80 个，Android 上 81 个，Web 上 73 个，其余标记为其他平台专用），用 `cucumber-js --parallel 2`（`pnpm test:e2e:<platform>:parallel`）运行，并与串行运行同一套测试（`pnpm test:e2e:<platform>`）对比。Apple M5 Pro（15 核，24 GB），macOS 26；iPhone 17 / iOS 27.0 模拟器；`Medium_Phone_API_37.0` 模拟器（emulator 37.2，`-gpu host`）；使用静态导出（`distDir`）的 Chromium；dev client 加载 Metro 开发版 bundle。2026-11-13 / 14。计时为整条命令的实际耗时，包括启动尚未运行的设备。

| 平台 | 2 个 worker：通过的运行 | 2 个 worker（s） | 串行（s） | 加速比 |
|---|---|---|---|---|
| iOS | **20 / 20** | 中位数 130.0（最小 128.9，最大 132.8） | 271.4 | 2.1 × |
| Android | **5 / 5** | 中位数 160.0（最小 159.3，最大 161.9） | 305.4 | 1.9 × |
| Web | **5 / 5** | 中位数 46.5（最小 46.4，最大 46.9） | 88.1 | 1.9 × |

- 每次运行的所有场景都通过了；没有出现需要处理的 "isn't responding" 对话框。Android 运行期间 host 端的 1 分钟平均负载：中位数 2.9，最大 3.9。
- **让 Mac 保持唤醒。** 第一次尝试 Android 和 Web 运行时，Mac 在夜间进入了空闲睡眠（显示器关闭 20 分钟后），运行仍在继续：此时进程只在每隔约 47 s 一次的短暂 "dark wake" 中运行，运行耗时长达 20 分钟，并出现超时和元素被遮挡。刚唤醒后的几次运行也慢了约 35 %（Android 上 217–241 s）。上面的数据是在 `caffeinate -dimsu` 下测得的。`pmset -g log | grep -E "Entering Sleep|Wake"` 可以显示某次运行是否受到影响。

在全部通过之前，这些运行发现并修复的问题（均在本阶段）：

| 症状 | 原因 | 修复 |
|---|---|---|
| Android：每台模拟器约 400 % CPU，system server 被 watchdog 重启 | 在 macOS 上，未带 `-gpu` 启动的模拟器用 CPU 渲染（`lavapipe`） | Quiesco 以 `-gpu host` 启动它们（`devices.android.gpu`），并对已经在用 CPU 渲染的模拟器发出警告 |
| 重新启动 App 时 Before 钩子超时 | cucumber 默认的 60 s 小于重新连接 + 重新启动所需的时间 | `registerQuiesco({ resetTimeoutMs })`，默认 180 s |
| Android："先不匹配、再用匹配的手指" 偶尔会一直等待 | 负载较高时，匹配的触摸落入了失败后传感器的锁定期，被丢弃 | 匹配的触摸之后，Quiesco 检查是否还有认证在等待（`dumpsys fingerprint`），如有则再次触摸（最多 3 次，并给出警告） |
| iOS：打开通知后 App 仍处于挂起状态 | 点击很可能落空，因为横幅还在滑入 | 等两次读取得到相同的位置后再点击；通知仍显示时再次点击（最多 3 次） |
| 20 次运行中有 17 次 iOS 点击以 `(the touch would reach UIView)` 失败 | Metro 监听了 `artifacts/` 和 `.expo/devices.json`；每次截图（以及每次 App 启动）都会让另一个 worker 的 dev client 在 App 上方显示 "Refreshing..." | `withQuiesco()` 把产物目录（`artifactsDir`）和 `.expo/devices.json` 加入 `resolver.blockList` |
| iOS：在旋转过设备的场景之后立即 push 的页面丢失了 | 下一个场景导航时，转回去的旋转动画仍在进行 | 下一个场景会等到窗口恢复原来的形状 |
| iOS：因为上一个场景让 App 处于挂起状态，场景失败 | 重置没有得到响应（`AGENT_TIMEOUT`），而只有连接断开才会重启 App | 场景开始前出现 `AGENT_TIMEOUT` 时也会重启 App |
