`examples/todo-app/bench/run.mts`（サンプルアプリの`pnpm bench:android`）で計測しました。requirements.md §8（性能 / 稳定性）を参照してください。数値はMetroから開発用JSバンドルを読み込むdev clientで計測したもので、開発モードのオーバーヘッドを含みます。リリースビルドではもっと速くなります。

計測している項目：

- **ソフトリセット（エージェント）**：エージェントが報告する`reset`の所要時間（ストレージの消去 → onResetフック → 再マウント → アイドル待ち）。requirements.md §6.5の目標：&lt; 500ms。
- **ソフトリセット（ホストでの往復）**：同じ処理を、ホスト側でWebSocketの呼び出しの前後で計測したもの。
- **同期込みのタップ**：ログイン画面でメールアドレスが空のまま`app.tap('login-button')`を実行し（ヒントが表示されるだけで、ネットワーク通信はない）、ホスト側で計測したもの。対象の解決 + 事前の同期、タッチ、事後のアイドル待ちを含みます。
- **サンプルのスイート全体**：サンプルのすべてのfeatureに対する`cucumber-js`。APKのインストールとアプリの起動を含みます。

補足：

- ソフトリセットは、どちらのモードでも目標の500msを大きく下回っています。
- nativeのタップは、jsのタップより約150ms長くかかります。内訳は、50msのタッチ保持、「ビューの動きが止まった」ことの確認（1フレーム間隔で2回のネイティブ検索）、そしてタッチ後のPressabilityの`minPressDuration`タイマー（130ms）です。押下状態がリセットされるまで、タイマートラッカーは正しくこのタイマーを待ちます。jsモードは`onPress`を直接呼び出すので、これらはいずれもかかりません。
- jsのタップの下限である約260msは、ほとんどが同期によるものです。アクションの前後に、2回のマクロタスクによるアイドル確認と、frame-stableトラッカー（2つの同一フレーム）があります。まだ最適化していません。

## Phase 6.12：並列実行 {#phase-612-parallel-runs}

サンプルのスイート全体（86シナリオ。iOSでは80、Androidでは81、Webでは73を実行し、残りは他のプラットフォーム用のタグ付き）を`cucumber-js --parallel 2`（`pnpm test:e2e:<platform>:parallel`）で実行し、同じスイートの直列実行（`pnpm test:e2e:<platform>`）と比較しました。Apple M5 Pro（15コア、24GB）、macOS 26。iPhone 17 / iOS 27.0のシミュレーター。`Medium_Phone_API_37.0`のエミュレーター（emulator 37.2、`-gpu host`）。静的Export（`distDir`）を使ったChromium。dev clientはMetroの開発用バンドルを使用。2026-11-13 / 14。まだ起動していないデバイスの起動も含めた、コマンド全体の実時間です。

| プラットフォーム | 2ワーカー：成功した実行 | 2ワーカー（秒） | 直列（秒） | 高速化 |
|---|---|---|---|---|
| iOS | **20 / 20** | 中央値130.0（最小128.9、最大132.8） | 271.4 | 2.1倍 |
| Android | **5 / 5** | 中央値160.0（最小159.3、最大161.9） | 305.4 | 1.9倍 |
| Web | **5 / 5** | 中央値46.5（最小46.4、最大46.9） | 88.1 | 1.9倍 |

- すべての実行ですべてのシナリオが成功し、「isn't responding」ダイアログに応答する必要は一度もありませんでした。Androidの実行中のホストの1分間ロードアベレージは、中央値2.9、最大3.9でした。
- **Macをスリープさせないでください。** AndroidとWebの最初の計測は、夜間にMacがアイドルスリープに入った後（ディスプレイが20分間オフ）も続いていました。この状態では、プロセスは約47秒ごとの短い「dark wake」の間しか動かず、実行に20分かかってタイムアウトや要素が覆われる失敗が起きました。スリープ解除直後の実行も約35%遅くなりました（Androidで217〜241秒）。上の数値は`caffeinate -dimsu`の下で計測したものです。実行が影響を受けたかどうかは`pmset -g log | grep -E "Entering Sleep|Wake"`で確認できます。

成功するまでに実行で見つかり、修正した問題（すべてこのフェーズで対応）：

| 症状 | 原因 | 修正 |
|---|---|---|
| Android：エミュレーターがそれぞれCPUを約400%使い、system serverがwatchdogによって再起動される | macOSでは、`-gpu`なしで起動したエミュレーターがCPUでレンダリングする（`lavapipe`） | Quiescoは`-gpu host`（`devices.android.gpu`）付きでエミュレーターを起動し、すでにCPUでレンダリングしているものには警告を出す |
| アプリを再起動している間にBeforeフックがタイムアウトする | cucumberのデフォルトの60秒が、再接続 + 再起動の時間より短い | `registerQuiesco({ resetTimeoutMs })`、デフォルトは180秒 |
| Android：「一致しない指の後に一致する指」がときどき永遠に待ち続ける | 負荷が高いと、一致する指のタッチが、失敗したタッチの後のセンサーのロックアウト期間に入って捨てられていた | 一致する指のタッチの後、Quiescoは待機中の認証が残っていないことを確認し（`dumpsys fingerprint`）、残っていればもう一度タッチする（最大3回、警告付き） |
| iOS：通知を開くとアプリが停止したままになる | おそらく、まだスライドインしている途中のバナーをタップし損ねていた | 2回読み取って同じ位置になったらタップする。通知がまだ表示されていれば再度タップする（最大3回） |
| 20回中17回の実行で、iOSのタップが`(the touch would reach UIView)`で失敗する | Metroが`artifacts/`と`.expo/devices.json`を監視しており、スクリーンショットのたび（およびアプリの起動のたび）に、もう一方のワーカーのdev clientがアプリの上に「Refreshing...」を表示していた | `withQuiesco()`が成果物ディレクトリ（`artifactsDir`）と`.expo/devices.json`を`resolver.blockList`に追加する |
| iOS：デバイスを回転させたシナリオの直後に遷移したページが失われる | 次のシナリオが画面遷移したとき、元の向きに戻す回転がまだアニメーション中だった | 次のシナリオは、ウィンドウが元の形に戻るまで待つ |
| iOS：前のシナリオがアプリを停止したままにしたため、シナリオが失敗する | リセットに応答がなく（`AGENT_TIMEOUT`）、アプリを再起動するのは接続が切れたときだけだった | シナリオの前の`AGENT_TIMEOUT`でもアプリを再起動する |
