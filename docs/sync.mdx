---
title: "Synchronization"
description: "What idle means, the trackers behind it, and what to do when an app never becomes idle."
---

Quiesco waits for the app to be **idle** before every query and assertion and after every action, so
steps never sleep or poll. "Idle" is decided inside the app by independent trackers; the app is idle
when all of them are idle twice in a row, one macrotask apart (a timer that fires and starts a request
in the same tick does not slip through).

## Trackers {#trackers}

| Tracker | Busy while | Notes |
|---|---|---|
| `network` | a `fetch` / `XMLHttpRequest` is in flight, a response body is being read, or a `WebSocket` / `EventSource` is connecting | `fetch` counts until the response arrives; a body read (`json()`, `text()`, …) started right after keeps it busy until the body is in, and a later read counts again. `expo/fetch` imported directly is tracked too (`withQuiesco()` swaps in a tracked re-export in e2e builds). A `WebSocket` / `EventSource` counts only until it opens, fails or closes; open connections never count (nor does the agent's own connection). `sync.ignoreUrls` excludes long polling, SSE, analytics. A `fetch` built on XHR (React Native) counts once. |
| `timer` | a `setTimeout` with a delay ≤ `sync.timerThresholdMs` (1.5 s) is pending | Longer timers (session expiry, polling every 30 s) do not block. `setInterval` only counts with `sync.countIntervals: true`. |
| `react` | React has uncommitted work: a root with pending lanes or a scheduled callback, or a pending task in React's scheduler (render work, passive effects) | Reads React's own bookkeeping through the DevTools hook — nothing in the app needs to change. |
| `idle-callback` | a `requestIdleCallback` is pending (and `InteractionManager` work on React Native versions that still have it) | |
| `native` (iOS) | a view-controller transition (navigation, modal presentation) runs, or the keyboard is moving / was just used | Reported by `@quiesco/native`; covers UIKit work invisible to JavaScript. "Keyboard moving" runs from UIKit's `keyboardWill…` notification to the matching `keyboardDid…`, at most the animation duration plus 0.5 s: iOS sometimes posts `keyboardDidShow` seconds late with the keyboard already in place (the device log then has `[Quiesco] keyboard: no Did notification …`). |
| `frame-stable` | the element tree (type, testID, text, rounded position and size of every element) changed during the last `sync.stableFrames` (2) frames | The fallback for animations on the UI thread (Reanimated, native-driver `Animated`). Only sampled while a call waits. |
| `native-module` (on when the build wraps native modules) | a native module method (TurboModule / NativeModules, Expo modules) has returned a promise that has not settled, or was given callbacks and has not called any yet (AsyncStorage's `multiSet`), for at most `sync.nativeCallThresholdMs` (2 s) | See [native module calls](#native-module-calls). |

Turn a tracker off with `sync: { trackers: { 'frame-stable': false } }`.

A call's timeline entry says what its wait for idle ended on, per tracker
(`native-module: RNCDatePicker.open() 1990ms`, `network: GET https://api.example.com/items (240ms)`): the
place to look when an action is slower than expected. It also says how the call's last wait ended: when
(device clock, to line up with the device log), its last checks with the trackers busy in each
(`+272ms busy: native-module | +276ms idle | +277ms idle (confirmed)`), and the native module calls that
started or settled during it (`RNCAsyncStorage.multiSet() +251ms→+266ms`): the place to look when an
action returned too early.

### Native module calls {#native-module-calls}

Without the `native-module` tracker, a pending native module call does not keep the app busy. A handler
that awaits one between two tracked steps looks idle in between:

```ts
// fetch: tracked
await api.login(email, password);

// native module promise: not tracked by default
await AsyncStorage.setItem(TOKEN_KEY, token);

// the next screen mounts and fetches in an effect
router.replace('/');
```

`tap('login-submit')` can return while `setItem` is pending, before the navigation and the next screen's
request have started. Either wait for what the next step needs (`await app.expectVisible('item-row-1')`),
or build the app with native modules wrapped: pass `nativeModules: true` to `withQuiesco()` in
`metro.config.js` (or start Metro with `EXPO_PUBLIC_QUIESCO_NATIVE_MODULES=1`) and restart Metro.

```js
module.exports = withQuiesco(getDefaultConfig(__dirname), { nativeModules: true });
```

The `native-module` tracker is on in such a build; nothing else needs to change. Its settings:

```ts
sync: {
  // a pending call counts for at most this long
  nativeCallThresholdMs: 2000,

  // "Module.method"; strings match as substrings
  ignoreNativeCalls: ['ExpoLocation.watch'],

  // off in a build that wraps native modules
  // trackers: { 'native-module': false },
}
```

Without the wrapping the agent leaves native modules alone, and the tracker counts nothing
(`trackers: { 'native-module': true }` then logs a warning, and `quiesco doctor` warns). In a build that
wraps native modules with the tracker turned off, the calls are still recorded: an action that returns
while one is pending lists it in its timeline entry, and a failed scenario's `idle-state.json` lists the
latest such actions (`nativeCallsNotCounted`), as a pointer to this race. The wrapping replaces a module's methods with JS functions. Gesture Handler, Reanimated
and Worklets call their modules' methods from worklets on the UI thread, which needs the native
functions, so those modules are never wrapped.

The tracker wraps the modules the app gets from React Native's `TurboModuleRegistry` and from Expo
(`requireNativeModule`) after the agent has loaded. React Native's own modules, taken during its startup,
are not tracked. Some native calls wait for the user — a permission request, an authentication sheet, a
picker — and stay pending until the test answers them. These never count by default: the permission
requests of Expo modules and `PermissionsAndroid` (`*.request…Permission(s)(Async)`), the date / time
picker dialogs (`RNCDatePicker.open`, `RNCTimePicker.open`), `ExpoLocalAuthentication.authenticateAsync`,
the share sheets (`ShareModule.share`, `ExpoSharing.shareAsync`), `ExpoWebBrowser.openBrowserAsync` /
`openAuthSessionAsync`, the image and document pickers, the alerts and action sheets (`AlertManager.alertWithArgs`,
`DialogManagerAndroid.showAlert`, `ActionSheetManager.show…ActionSheetWithOptions`). Native-driver
animations (`NativeAnimatedModule`), which call back when the animation ends, never count either.
`ignoreNativeCalls` adds to them;
`defaultIgnoreNativeCalls: false` counts them too. Any other call stops counting after
`nativeCallThresholdMs`, so a step that opens such a UI waits that long at most: the timeline names the
call (`native-module: Module.method() 1990ms`) to add to `ignoreNativeCalls`.

How the React tracker works, and why the agent must load before React Native's renderer, is described in
[docs/spikes/02-react-idle.md](https://github.com/h2nology/quiesco/blob/main/docs/spikes/02-react-idle.md). `withQuiesco()` in `metro.config.js` takes care
of the loading order (React Native 0.88 loads its renderer before the app's entry file).

## When the app never becomes idle {#when-the-app-never-becomes-idle}

A call that waits longer than `sync.timeoutMs` (10 s) fails with `SYNC_TIMEOUT`, listing what was busy:

```
App did not become idle within the 10000ms timeout. Busy:
  - network: GET https://api.example.com/todos (10012ms)
  - timer: setTimeout(poll, 1000ms), fires in 420ms
  - frame-stable: element tree changing: stable for 1/2 frames (580 frames sampled in 9960ms)
    last change: first difference at node 12: Text "Loading 41%" … → Text "Loading 42%" …
```

What to do depends on the tracker:

- **network** — a request that never ends (long polling, a stalled backend): add it to `sync.ignoreUrls`,
  or fix the backend / mock. Use `MOCK_STALL`-style knobs in your mock server to reproduce it on purpose.
- **timer** — a short timer that is re-armed forever (a polling loop with `setTimeout`, a toast that
  re-schedules itself). Skip sync for that step (`{ sync: false }`), turn the timer tracker off for the
  scenario (`this.app.sync.disableTracker('timer')`), or stop the loop in e2e builds. Only timers up to
  `sync.timerThresholdMs` count, so lowering it below the loop's delay works too, but for every timer
  that short in the whole app.
- **frame-stable** — something keeps moving: an endless animation (spinner, shimmer, marquee, a slow
  decorative glow) or a counter. The report names the first element that changed. If the element is
  decoration, give it a testID and list it in `sync.ignoreElements` — it and its subtree are left out of
  this check, everything else still is. Otherwise call the step with `{ sync: false }` and assert what
  you need afterwards, or disable the animation in e2e builds. If `frames sampled` is very
  low for the time waited, the UI thread is starved (an overloaded emulator), not animating.
  `recent changes` lists the latest changes (time into the wait, node count, first different node).
  When the same element keeps changing back and forth, even while other parts of the tree change, the
  report names it. If an element is added and removed each time, it is usually a list: a `FlatList` / `VirtualizedList` without
  `getItemLayout` and with rows of slightly different heights can keep adding and removing the item at
  the edge of its render window after a scroll. A longer `timeoutMs` does not help; `getItemLayout`
  or fixed row heights usually stop it. Quiesco still counts this as busy, since it is real activity.
  frame-stable only samples while a call waits, so `idle-state.json` shows it idle after a timeout;
  its `lastWait` keeps what it reported when the wait ended.
- **react** — a render loop (a state update in an effect without a guard) never settles: a real bug.

`AGENT_TIMEOUT` is different: the agent did not answer at all, usually because the JS thread is blocked
by a long synchronous task.

## Skipping sync for one call {#skipping-sync-for-one-call}

```ts
// do not wait before / after
await this.app.tap('start-spinner', { sync: false });

// assert while it spins
await this.app.expectVisible('spinner', { sync: false });
```

## Platform notes {#platform-notes}

The same trackers run on all three platforms. On the web the agent reconnects after a full page load and
the host waits for it transparently; with Expo Router's static output the app is considered ready after
hydration. The `native` tracker exists only on iOS. See [platform differences](./platforms).
